# Konti — evaluation and verification evidence

Curated English summary of the Konti development log (Hungarian original: [full development log](docs/DEVELOPMENT-LOG.md); project overview: [README](README.md)).
It collects the entries that concern AI evaluation, measurement errors and the separation of claims from evidence.
Dates are local Budapest dates. Numbers are historical snapshots tied to the cited run or release.

## Context

Konti is a mini ERP for a container rental and transport company: orders, dispatch planning, driver tasks,
a shared operational chat, GPS from driver tablets and digital delivery notes. It has been in a live pilot
with the company's dispatcher since November 2026.

Note: links to `github.com/beeaibuild/kontener-app` PRs and CI runs refer to the private repository and do not open publicly;
the PR numbers are kept as stable identifiers.

The AI layer recommends; it does not decide. The model chooses only from candidates that the server has
generated by rule. The server checks permissions and business validity. The operator accepts, sees a fresh
preview, and confirms execution in a separate step. Recommendations, decisions and rejection reasons are
stored unchanged and audited. Details (Hungarian): [operational recommendations](docs/operational-recommendations.md),
[initial assignment recommendation](docs/initial-assignment-recommendation.md), [decision telemetry](docs/initial-assignment-telemetry.md),
[transaction lock protocol](docs/transaction-lock-protocol.md).

Konti also interprets natural-language dispatch messages (originally from the team's Viber chat). Most of the
evaluation work below concerns that interpretation task. Interpretation safety rules: [eval safety V2](docs/konti-viber-eval-safety-v2.md).

## How to read this

- **In the code:** supported by a merged GitHub PR. This is not the same as a successful production deployment.
- **Verified:** only within the limits of the specific test, CI run, staging smoke test or other cited evidence.
- **Open:** a physical test, provider integration, deployment or business effect that still has to be shown.

## 1. Cases where reported results and evidence diverged (recorded 31 October 2026)

**Interpretation boundary:** these cases do **not** prove that an AI agent invented a test run or a PASS result.
What they show is the need to keep apart the report, the run artifact, test coverage and the real system state.
A hallucination claim requires a specific, retrievable model statement and run evidence that contradicts it.

### PR #58 — missing evidence for a real provider benchmark (11–13 September 2026)

**Situation:** the preceding draft PR #57 reported seven real `gpt-4.1-mini` provider runs and seven FAIL benchmark
verdicts. It argued against merging the tuned policy because critical safety results got worse despite a better
average score. These numbers could not be reconstructed afterwards from raw run artifacts, so **they are not treated
as verified model performance**. The scripted oracle and green CI of the following PR #58 did not replace a real
provider benchmark.
**Check:** when the seven runs were re-checked, the expected run files and the provider key were not available in
the checking environment; reproducing the metrics was blocked. The PR itself states: "No real-provider benchmark was run."
**Lesson:** a scripted test PASS is not a real provider benchmark. Without the raw artifact a result is
**unverified**, not automatically "invented".

### PR #59 — two real, archived provider campaigns that can no longer be re-scored (14 September 2026)

**Situation:** separately from the unreconstructable #57 claims, the manual workflow of #59 ran two
`gpt-4.1-mini` campaigns documented by GitHub Actions, on two different frozen commits.
**Check:** both GitHub jobs SUCCESS, 7/7 real provider runs and 140/140 scorable cases; the benchmark's semantic
verdict was FAIL on both. The saved job logs report 0 critical error cases in the first campaign and 10 in the second.
This is a **confounded comparison**: neither a proven model regression nor a proven scorer effect. Between the two
commits the scorer (`scoring.ts`) changed at the same time as the content passed to the model and its processing
(`policy.ts`, `providers.ts`, `semantic.ts`). The individual effects cannot be identified. Re-scoring the earlier raw
outputs with the new scorer could have isolated the effect of the measuring instrument; estimating the effect of the
input/policy change would have needed a further controlled run. The upload of the archives is confirmed by the run log,
but after 14-day retention the raw JSON/stderr files are gone; independent case-level re-scoring **is not possible**.
**Lesson:** change only one factor at a time in a controlled comparison. Keeping raw model outputs makes it possible
to swap the scorer later and re-score without new API calls. A successful run and upload alone is not durable
auditability.

### PR #74 — test coverage gaps found despite green CI (21 September 2026)

**Situation:** the full CI of a provenance/idempotency implementation passed, but a targeted expert review found
eight further blocking risks (cross-user/mode idempotency, semantic fingerprint, forged sidecar, source race,
database invariants). The PR documents later fixing commits and a new exact-tree CI.
**Lesson:** green CI proves that a given test suite passed, not the full safety claim. Verification also has to look
for invariants that are not tested.

### PR #89 — a partial test PASS is not a full CI PASS (4 October 2026)

**Situation:** for a reassignment deadlock fix, the targeted access-control and reassignment regressions passed,
but the full P63 run stayed **FAILURE**: 2599 tests passed and one unchanged AI orchestrator test failed
(expected provider calls 1, actual 0; `AUTHORITY_CONTEXT_STALE`). After the failed Vitest gate, production build,
E2E and Docker did not run.
**Lesson:** a targeted test PASS is not the same as passing the full gate. It is **not proven** that an AI agent
claimed PASS for a test it did not run; that would require the original model message together with a contradicting
run log.

### PR #136 — false STALE approval error (19 October 2026)

**Situation:** unordered database lists for the same business state could produce different recommendation hashes,
so a valid recommendation could be closed as STALE.
**Check:** a regression with reversed database order failed on the original implementation and passed on the fix.
The exact field behind the discrepancy seen on staging could not be proven forensically afterwards.
**Lesson:** whether a model recommendation can be approved also depends on deterministic server-side state handling.
A reproduced failure mechanism does not justify calling the full cause of the staging incident proven.

## 2. Natural-language interpretation benchmark (4–8 November 2026)

### 4 November — real run, offline reproduction, scorer changes V2/V3

One 20-case run with `gpt-4.1-2025-04-14`, temperature 0, on the user's PC with separate permission.
V1 result: 56.02 points, 20 scorable cases, no critical safety failure, benchmark not passed.
The export keeps exact case-level inputs, filtered provider outputs, replayable predictions and a SHA-256 manifest.
Independent checks of the 45 checksums and offline re-scoring succeeded; all 20 case results matched the original.

**Measurement gaps found in the scorer:** for some labels V1 did not flag a swapped driver binding; the mere presence
of a condition could earn acceptance even when its actor or meaning differed; simple text matching of conditions
penalised a correct paraphrase.

**Fixes:** V2 added label-independent role-binding checks and a strict condition gate; V3 checks a single atomic
return condition by predicate and polarity. On the **same frozen real responses**, V2 and V3 both gave 54.77 points.
**The difference from V1 is a scorer effect; it proves neither model degradation nor model improvement.**
All 20 cases replayed identically with an empty API key and network access disabled.
Sources: [measurement protocol](docs/viber-eval-run-protocol.md), [export format](docs/viber-eval-artifacts.md),
[V2 change](docs/viber-safety-v2-change.md), [V3 change](docs/viber-condition-meaning-v3.md).

### 5 November — synthetic controls and a separate evaluator audit

Eight synthetic control cases, real run: 5/8 automatic pass, 8/8 scorable. Because evaluator errors were found,
a separate, retrospective V2 audit was made on the same responses: structural content 7/8, labelling 6/8,
permissions 8/8, combined 5/8. The V1 report was left unchanged; **V2 does not prove model improvement.**
In one case the model bound a named person as recipient without evidence; V2 now flags this.

Successive, separately authorised 20-case runs scored with V3: 55.13 → 56.83 → 59.60 → 60.67.
The 59.60 run gave a critical flag on a conversational case; the last did not. Every run was a benchmark FAIL,
not release compliance.
Sources: [controls V1](docs/viber-controls-v1.md), [controls V2 audit](docs/viber-controls-v2.md),
[interpretation contract review](docs/viber-interpretation-contract-review.md).

### 6–7 November — ten real cases: automatic checks versus manual review

Ten new real cases (pseudonymised). Automatic constraint check: 9/10, all responses scorable.
**Manual review:** seven cases had correct essential content; in three the model assigned an unjustified executor,
misread a street-type word, or reversed a spatial relation and returned information instead of an instruction.
**This is not 90% content accuracy.** Three observed wrong responses became regression fixtures.

Two further re-runs after prompt changes gave mixed results: some errors fixed, others shifted to a different label.
Re-scoring the three saved runs with the shared V3 scorer: 8/10 → 8/10 → 9/10, raw responses unchanged.
Source: [real cases, method and review](docs/viber-real-selection-v1.md).

**Decision (7 November):** these ten cases (R01–R10) are now explicitly a **development set**. The 9/10 result is kept,
labelled as an automatic constraint check measured on the development set, **not a generalisation result**.
A held-out protocol was fixed in advance: quotas for days, senders and message types; three repetitions;
a case passes only at 3/3; 1/3–2/3 cases are reported separately as unstable.
The runner records a freeze manifest with the full commit and source hashes; new sample selection may happen only
after freezing; expectations are never sent to the provider.
Sources: [held-out protocol](docs/viber-holdout-protocol-v1.md), [held-out runner](docs/viber-holdout-runner-v1.md),
[portable artifacts](docs/viber-portable-artifacts.md).

### 8 November — held-out set

For the frozen commit, 18 new event windows, 43 pseudonymised messages and 35 manual expectations were prepared
**before** the run (4 working days, 3 drivers, chronological quotas). Raw sources and the name map are not in Git.

**Result:** 3 × 18 real responses, automatic 6/18, 5/18, 5/18; with the fixed rubric 4 stable, 2 fluctuating,
12 FAIL. Offline re-scoring of 246 hashes and 54 cases matched.
Alongside instruction/actor and context-loss errors, annotation disputes also appear; the gold labels were not changed.
**These 18 cases are now development data.** A new freeze and a new held-out set are needed for any future claim.
Targeted fix after the run: [reference contract V2](docs/viber-reference-contract-v2.md).

## 3. Separating behaviour change, evaluator change and run-to-run variation (recorded 14 November 2026)

**Case 1 — evaluator error.** The baseline report raised 19/19 critical flags, with documented false evaluations of
actor, sequence and condition. After the evaluator fix, the re-measurement had 20/20 scorable cases, 0 critical,
50.63 points, against 40.84 earlier. **This difference is not a pure evaluator effect:** fresh model responses and a
schema-matching fix were also involved.
Reports: [baseline report](reports/), [fix report](reports/).

**Case 2 — variation.** Seven runs × 20 cases with an unchanged evaluator and model alias: 45.70–51.45 points,
mean 48.77, sample standard deviation 2.22 points; the 50.63 above is the first of these runs. One case lost a
critical condition in two of the seven runs. There is no backend fingerprint, so a backend, numerical or stochastic
origin of the variation cannot be separated.
Report: [seven-run report](reports/).

**Evidence boundary:** these are retrievable historical reports, not independently reconstructed raw runs now.
A hash in a report does not on its own replace the original file.

**Research question that came out of this:** how can a change in behaviour, a change in the evaluator and run-to-run
variation be separated? No improvement relative to the noise band is claimed as verified.

## 4. Lasting design decisions

| Decision | Reason and limit |
| --- | --- |
| The AI recommends; a human approves and confirms execution | Model output is not a direct business command; fresh server-side permission and state checks are mandatory. "Accept" and "execute" are two separate decisions. |
| The LLM gets only permitted, minimised and versioned context | Context is kept apart from instructions and permissions; raw chat is not a source of permissions. Interpretation is not a source of truth for authority. |
| Operational writes use a single lock order and targeted admission | Control of concurrent changes, deadlocks and stale state; no general automatic retry. |
| Schema changes only through versioned, forward-additive migrations | Production data is preserved; rollout is reproducible. |
| PR/CI/staging confirmation and production deployment are separate events | A merge and a green test do not prove the live service. Procedure: [main merge and deployment](docs/main-merge.md), [migration workflow](docs/migration-workflow.md). |
| Raw model outputs are kept with hashes for offline re-scoring | A scorer can be changed and re-run without new provider calls; replay is checked with no API key and network disabled. |

## 5. Short timeline

- **July 2026:** order and operations core: public ordering, pricing, admin assignment, driver tasks and statuses, audited transactional state machines, versioned migrations, staging, backup/restore proof. Built before any AI feature.
- **August–early September:** daily mini-ERP operation: notifications, internal transport tasks, dispatch map, weekly capacity, rule-based reorganisation suggestions accepted by a human.
- **September:** AI foundations: versioned, minimised AI context contract, multi-role revocable sessions, provider-independent read-only AI runtime; policy, structured output, test data and evaluation gates for message interpretation. Shared operational chat with permission limits.
- **Early October:** approvable, audited Konti AI V1: protected operational writes, stored recommendation and decision, rejection reasons, explicit preview and confirmation, at-most-once execution; 7/30/90-day metrics.
- **Mid October:** driver tablet and native Android GPS with offline buffer; same-day assignment recommendations using GPS and Google road estimates; AI recommendation at first assignment of a new order (driver, truck, date), with every decision recorded as accepted or modified.
- **Late October:** staged tests of proactive and reassignment recommendations, delay cascade analysis behind an admin master switch.
- **November:** interpretation benchmark work above; independent code review of authentication, migrations, AI audit chain, tablet pairing and concurrency, with all findings fixed; AI audit tables made append-only at database level; weekly frozen telemetry snapshots with SHA-256; voice/text order capture with operator review; live pilot with real drivers and tablets.

## What is not claimed

Green CI does not prove physical Android reliability or real logistics savings. Telemetry is suitable for tracking
but does not by itself prove savings. Estimated time gains in staging tests are not realised business benefit.
The real operational value of the AI recommendations is still to be measured in the live pilot.
